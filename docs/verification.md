## 오늘 학습 배치·초안·변경 비교 검증

### 실제 검증

## 계획 입력 간소화와 빈 학습일 원인 확인

2026-11-15에 앱에서 이미 공부한 과목(진도·누적 학습), 학습량 산정 근거, 계획 계산 기준을 제거했다. 미리보기의 중복 계산 안내도 제거했다. 과목 이해도, 미리보기, 변경 비교와 명시적 저장은 유지한다. 하루 입력 이름은 기존 서버의 의미에 맞게 하루 최대 학습 시간으로 표시한다.

### 실제 코드 실행과 백엔드 무결성

- 앱은 기존 review-based API에 입력한 dailyMinutes와 studyWeekdays를 전달한다. 서버는 카탈로그의 기준시간으로 다시 검증·계산한다. 검증된 후기 기준시간을 적용할 수 없으면 기존 잠정값을 사용하므로 모든 기준시간이 실측값이라는 의미는 아니다.
- 기존 MultiGoalPlanCalculator.java를 수정 없이 읽어 임시 폴더로 컴파일·실행했다. 기본 과목 필요량은 기준시간 × 60 × 이해도 보정(낮음 1.3 / 보통 1.0 / 높음 0.7)이다. 하루 시간은 상한이고, 기간에 분산한 수요가 기본 45분 미만이면 누적될 때까지 날짜를 건너뛴다. 선택하지 않은 요일과 시험 당일은 제외하며, 긴 준비 기간에는 시험 직전 최대 7일의 여유도 둔다.
- 다음 값은 실제 사용자 데이터나 외부 통계가 아닌 **SAMPLE 가상 입력**으로 Java 코드를 실행한 결과다. 기준 5시간인 4과목, 이해도 보통, 진도·누적 학습 0, 매일 가능, 고정 시작일 2026-11-15를 사용했다. 모든 경우 총 1,200분이 배정됐고 하루 상한을 넘지 않았다.

| GET /dashboard/study-stats | 미구현. 실제 시간 합계와 날짜별 합계는 기존 DB로 구현 가능 | 기간 해석·날짜별 항목 구조·빈 날짜 처리. `completionRate`의 의미·계산 기준은 미정 |

현재 `/auth`, `/users/me`, `/api/chat/...`처럼 여러 경로 계열을 사용한다. 제시된 두 경로가 잘못된 경로이거나 반드시 `/api`를 붙여야 하는 것은 아니다. 기존 매핑과 충돌하지 않으며 새로운 매핑으로 정의할 수 있다.

### 저장 명세의 불일치

`STUDY_SESSIONS`에는 `session_id`, `user_id`, `task_id`, `study_date`, `start_time`, `end_time`, `actual_minutes`, `input_method`, `digestion_level`이 있다. `subject_id`와 `plan_id` 열은 없다. `study_date`·`actual_minutes`·`task_id`와 시각은 nullable이다.

| 제시한 값 | 현재 저장 경로 | 검토 결과 |
| --- | --- | --- |
| studyDate | STUDY_SESSIONS.study_date | 날짜 문자열 형식, Asia/Seoul 기준, 미래 날짜·소급 허용 정책을 정해야 한다 |
| durationMinutes | STUDY_SESSIONS.actual_minutes | 이름이 달라도 DTO 매핑 가능. 필수 정수·양수·상한을 서버에서 검증해야 한다 |
| subjectId | task_id → STUDY_PLAN_DETAILS.certification_subject_id | 직접 저장할 열이 없다. 과목 ID만으로 날짜별 계획 항목을 유일하게 결정할 수 없다 |
| planId 선택 | task_id → STUDY_PLAN_DETAILS.plan_id | 직접 저장할 열이 없다. 계획 ID와 과목 ID로 특정 할 일을 임의 선택하면 안 된다 |
| sessionId 응답 | STUDY_SESSIONS.session_id | 자동 생성 키를 반환 가능 |
| 저장된 시간 응답 | actual_minutes → durationMinutes | 실제 저장된 정수 분으로 반환. 계획 배정 분과 구분해야 한다 |

정상적인 현재 관계는 `STUDY_SESSIONS.task_id → STUDY_PLAN_DETAILS.task_id → plan_id / certification_subject_id`다. 실제 공부한 날짜와 원래 계획 날짜는 다를 수 있으므로 `studyDate`를 `scheduled_date`로 취급해 항목을 추측해서는 안 된다. 같은 과목은 여러 날짜·계획에 반복될 수 있고, 계획 항목의 복합 유일성 제약도 없다.

`taskId=null`인 수동 기록은 날짜·분을 저장할 수 있다. 그러나 원문의 임의 `subjectId`와 선택 `planId`까지 독립적으로 보존하는 저장 경로는 없다. 이를 그대로 지원하려면 별도 과목/계획 연결 구조를 추가하거나 기능 범위를 계획 항목 연결로 좁혀야 한다. 숨은 계획·가짜 할 일을 자동 생성하거나 다른 용도의 열에 ID를 넣는 방식은 제외한다.

계획 카탈로그에는 nullable `Long subjectId`가 있다. `MultiGoalPlannerController`는 정보처리기사 2027년 필기를 기존 2026년 과목 ID와 혼용하지 않도록 임시 카탈로그로 제공하고, 이 경우 과목 ID가 null일 수 있다. `ChatPlanStore.replace`도 이를 허용해 과목명과 함께 계획 항목을 저장한다. 따라서 `subjectId`를 무조건 필수로 하는 명세는 현재 앱의 모든 계획을 지원하지 못한다. 과목 ID가 null인 서로 다른 과목을 하나의 과목으로 합쳐서도 안 된다.

현재 저장 계획 응답의 `Task`에는 날짜·시험명·과목명·배정 분만 있다. `taskId`가 없고 Flutter의 `StudyTask`에도 식별자가 없다. 계획에 연결해 기록하려면 기존 조회 응답의 식별자 확장에 대한 담당자 협의 또는 한결 담당의 별도 읽기 API가 필요하다. 기록 POST 세 개의 명세만 추가한다고 현재 앱에서 특정 할 일을 선택·저장할 수 있는 것은 아니다.

### DB를 유지하는 1단계 검토안

다음은 구현 승인이 아닌 명세 보완 제안이다.

- POST 입력: 필수 `studyDate`, `durationMinutes`, 선택 `taskId`. 사용자 ID는 입력받지 않고 인증된 사용자에서 결정한다. 계획 연결 시 `taskId`를 받고 과목·계획 ID는 서버가 관계에서 도출한다.
- 계획 없는 수동 기록을 허용한다면 `taskId=null`, 과목·계획도 null인 기록으로 명확하게 표현한다. 임의 과목까지 지정하는 수동 기록을 포함하려면 기존 DB만 사용하는 이 안으로는 부족하다.
- 이 POST는 수동 기록 또는 종료 결과 저장이다. 입력에 없는 시작·종료 시각을 현재 시각과 공부 분으로 꾸며 넣지 않는다. `input_method`의 값과 결정 주체를 명세에 적는다.
- POST 응답은 `sessionId`, `studyDate`, `durationMinutes`, nullable `taskId`·`planId`·`subjectId` 및 필요 시 `subjectName`을 공통 응답의 `data` 안에 담는다.
- 통계 1단계는 `totalMinutes`, 날짜가 포함된 `dailyStudyMinutes`를 우선 제공한다. `completionRate`는 정의 전까지 제외하거나 nullable로 명시한다.

원문의 `subjectId`를 유지하면서 범위를 그대로 보장하는 안과 위의 DB 유지 안은 서로 다른 계약이다. DB를 바꾸지 않는다는 이유로 지원하지 못하는 입력을 받았다가 조용히 버리는 구현은 안 된다.

### 조회 명세에서 확정할 사항

| 항목 | 권장 명세안 |
| --- | --- |
| 본인 조회 | JWT의 userId로 모든 SQL 제한. 요청 userId로 다른 사람 기록을 조회하는 기능 제외 |
| 날짜 | YYYY-MM-DD, 시작·종료일 모두 포함, 시작일 ≤ 종료일. 기간은 실제 study_date 기준 |
| 페이지 | 예: 0부터 시작, 기본 20개·최대 100개. 제안 값이며 현재 구현된 규칙이 아님 |
| 정렬 | study_date DESC, session_id DESC로 날짜 동률의 순서를 고정 |
| 응답 | data 객체 안 items, page, pageSize, hasNext. 전체 개수를 제공한다면 동일한 본인·기간 조건으로 count |
| 범위 밖 페이지 | 빈 items와 hasNext=false. 조회 실패와 빈 목록을 구분 |
| 계획 미연결 | taskId·planId·subjectId는 null 허용. 없는 ID를 0 또는 가짜 ID로 대체하지 않음 |
| 과목 정보 누락 | 과목 ID가 null이어도 계획 항목의 이름을 보일 수 있음. 알 수 없는 정보를 실제 과목 ID로 추정하지 않음 |

오프셋 페이지는 새 기록이 들어오는 동안 앞 페이지가 이동할 수 있다. 날짜와 ID의 고정 정렬은 동률 문제를 해결하지만 조회 전체의 일관된 스냅샷을 보장하지 않는다. 그런 보장이 필요해질 때 cursor나 조회 기준 시점을 별도로 정의한다.

Flutter `PassApi._send`는 `{status, code, data}`를 해석하고 `data`를 객체로 읽는다. 본문 전체나 data에 원시 목록 배열만 반환하면 이 읽기 방식과 맞지 않는다. 명세의 ‘목록’이라는 설명만으로 실제 JSON 형태를 확정하면 안 된다. 기존 서버의 성공 응답은 `ResponseUtil.SUCCESS`의 HTTP 200이며 생성 시 다른 상태를 선택한다면 HTTP 상태와 본문 code도 함께 정의한다.

### 통계와 completionRate

`totalMinutes`는 본인의 조회 기간 `actual_minutes` 합계여야 한다. 계획 저장 응답에 있는 `totalMinutes`는 배정 시간이며 실제 공부시간의 대체 데이터가 아니다. 시간 통계만 제공하는 1단계에는 새로운 통계 테이블이 필수적이지 않다.

- `dailyStudyMinutes[]`의 각 항목은 날짜와 실제 정수 분을 함께 가져야 한다. 날짜 없는 숫자 배열은 누락일을 식별할 수 없다.
- 기록 없는 기간의 합계는 0, 그래프용 날짜별 목록은 요청 기간을 오름차순으로 채우고 빈 날짜를 0분으로 정의하는 안을 권장한다. 0분은 ‘기록된 공부시간 없음’이며 학습 완료·휴식·계획 없음의 판정이 아니다. MariaDB의 빈 집합 SUM은 NULL이므로 이 정책에는 명시적인 0 처리가 필요하다. [MariaDB SUM](https://mariadb.com/docs/server/reference/sql-functions/aggregate-functions/sum)
- `period`와 날짜를 같이 받는다면 우선순위를 묵시적으로 두지 않는다. 예: LAST_7_DAYS·LAST_30_DAYS는 서울 기준 오늘을 포함하는 최근 일수, CUSTOM만 startDate·endDate를 필수로 받는다. 충돌 입력은 400으로 처리하는 안이다. 응답에는 확정된 startDate·endDate·timezone을 제공한다.
- 기존 nullable 공부 날짜·분이 실제 행에 존재하는지는 이번에 조회하지 않았다. 신규 입력의 필수 검증과 함께 기존 NULL/비정상 값 처리 정책이 필요하며, 비정상 기록을 정상적인 0분 공부로 꾸미지 않는다.

`completionRate`는 다음 중 무엇인지 제시한 명세로 결정할 수 없다.

| 가능한 의미 | 현재 근거와 한계 |
| --- | --- |
| 공부시간 / 계획시간 | 정의를 추가하면 계산 가능하지만 ‘계획 시간 달성률’이다. 이해도·학습 내용의 완료율이 아니다 |
| 완료한 할 일 수 / 전체 할 일 수 | 현재 계획 항목에 명시적인 완료 상태와 완료 시각이 없다. 시간 도달로 완료를 추정한다면 별도 제품 규칙이 필요하다 |
| 과목 학습 진도 | GOAL_SUBJECTS.progress_rate 열은 있지만 이를 개인 기록으로 갱신하는 현재 구현을 발견하지 못했다. 열의 존재가 신뢰할 수 있는 진도 API를 의미하지 않는다 |

시간 달성률을 선택하더라도 현재/과거 계획의 범위, 예정일과 실제 기록일의 기준, 비계획 공부 포함 여부, 분모 0, 100% 초과, 소수점 반올림을 명시해야 한다. 계획 60분에 공부 90분이면 단순 비율은 150%이며 숙련도가 150%라는 뜻이 아니다. 계획이 없을 때는 비율을 0%나 100%로 꾸미기보다 null로 정의하는 안을 권장한다.

계획과 기록을 조인한 뒤 `SUM(estimated_minutes)`를 바로 계산하면 기록 수만큼 계획시간이 반복된다. 계획량과 실공부량을 각각 정해진 범위로 집계한 뒤 결합해야 한다. 현재 활성 계획으로만 실공부 기록을 제한하면 REPLACED 계획에 연결된 과거 기록이 빠진다. 개인 총 공부시간과 특정 계획의 달성률은 집계 범위를 구분해야 한다.

### 인증과 데이터 검증

- 현재 팀 인증은 서버 세션 쿠키가 아니라 `Authorization: Bearer <JWT>`다. 새 API도 기존 JwtPrincipal과 응답·오류 형태를 따라야 한다. `/study/**`·`/dashboard/**`를 공개 경로에 추가할 이유는 없다.
- 인증이 됐다는 사실만으로 전달된 taskId·planId가 본인 것이라는 보장은 없다. 기록 사용자, 계획 항목 사용자, 상위 계획 사용자, 전달한 과목·계획 간 일치를 서버에서 확인해야 한다. DB의 각각의 외래 키는 이 소유권 일치를 강제하지 않는다. [OWASP 객체 단위 권한 검증](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/)
- studyDate 필수·형식, durationMinutes 필수·정수·양수, ID 존재·양수, 날짜 범위·페이지 크기를 검증한다. 실제 기록 시간의 상한과 같은 날짜 합계 제한은 별도 결정한다. 계획의 ‘하루 최대 학습 시간’은 실제 기록 시간을 임의 절삭하는 기준이 아니다.
- 수동 입력은 시작·종료 시각이 없으므로 시간대 겹침까지 검증할 수 없다. 자정을 넘는 실측 타이머 기록은 서울 날짜별 분배와 UTC 시점 기록을 별도 명세로 다뤄야 한다.
- 미인증·만료 401, 권한 위반 403, 잘못된 입력 400 등 기존 JSON 오류 규칙을 명시한다. 타인 자료를 숨기기 위해 404를 선택한다면 그 정책도 일관되게 정해야 한다.
- 현재 GlobalExceptionHandler는 `MethodArgumentNotValidException` 등을 400으로 처리하지만 `HandlerMethodValidationException`을 별도 처리하지 않는다. 새 쿼리 파라미터에 직접 @Min 등의 제약을 붙이는 방식은 이 예외를 발생시킬 수 있어 일반 Exception 처리의 500으로 빠질 가능성을 검증해야 한다. 현재 코드에서 이 새 API의 오류가 실제 500이라고 확인한 것은 아니다. [Spring MVC 6.2 검증](https://docs.spring.io/spring-framework/reference/6.2/web/webmvc/mvc-controller/ann-validation.html)
- 기존 팀 SecurityConfig에는 CSRF disable이 있어 제공된 AGENTS.md의 ‘CSRF를 끄지 않는다’는 규칙과 불일치한다. 이 기존 상태는 이번 검토에서 수정하지 않았다. 신규 API를 위해 보안을 더 완화하는 안도 제시하지 않는다.

### 중복 저장과 계획 변경

원문의 POST에는 요청 재전송을 구별하는 키가 없다. 통신 시간 초과 후 다시 보내면 같은 공부가 두 번 저장될 위험이 있다. 같은 날짜·과목·분이 같아도 실제로 두 번 공부한 정상 기록일 수 있어 이 값만으로 중복을 삭제할 수 없다.

모바일에서 재시도에도 정확히 한 번 저장되는 동작을 보장하려면 요청 키의 유효 범위·동일 키의 다른 본문 처리·결과 재사용과 영속적인 유일성 보장이 필요하다. 현재 STUDY_SESSIONS에는 그 키가 없다. 재시작·여러 서버에 걸친 중복 방지를 보장한다면 별도 열/테이블 등의 영속 구조 검토가 필요하다. 클라이언트의 버튼 잠금만으로 해결됐다고 보고하면 안 된다.

현재 ChatPlanStore는 재저장 시 이전 계획을 REPLACED로 남기고 새 계획·할 일을 생성한다. `version_no`를 MAX+1로 정하지만 사용자 행 잠금이나 revision의 조건부 갱신 프로토콜은 발견하지 못했다. 제공된 팀 규칙의 기록·계획 승인 직렬화를 충족하려면 관련 작성자들이 같은 사용자 잠금·버전 규약에 참여해야 한다. 새 기록 API만 잠가서는 그 규약 전체를 충족했다고 할 수 없다. 교체된 계획에 대한 추가 기록 허용/409 정책과 과거 기록 조회 보존도 명세에 넣어야 한다.

STUDY_SESSIONS의 실제 인덱스는 기본 키와 사용자·할 일 외래 키 인덱스다. 사용자·기간·정렬 쿼리의 `(user_id, study_date, session_id)` 같은 복합 인덱스는 데이터가 증가할 때 검토할 항목이다. 이번에 성능을 측정하지 않았으므로 느리다고 단정하거나 필수 스키마 변경으로 분류하지 않는다.
